# Stage 3: Mockups

Runs when `ui_change` is true. Backend-only work skips this file entirely.

Read `rules/mockups.md` for the count and the format, and `docs/SCREENS.md` for what makes a
screen look machine-made. Both are canonical; this file is the procedure.

## Where they live

```bash
mkdir -p .mockups/build-<slug>
grep -q '^\.mockups/' .gitignore 2>/dev/null || echo '.mockups/' >> .gitignore
```

The `.gitignore` line is the step everyone forgets, and it is how mockups reached two repos.

Mockups are standalone and sit outside the running app. They are a cheap contract to point at
before real code exists; making them real costs the hours they exist to save. The build in
stage 5 goes into the real component instead.

## Tokens first

```bash
[ -f design-system/MASTER.md ] && echo FOUND || echo NONE
```

Found: its palette, type, spacing and layout rules are hard constraints on every variant in
the set. Say which file you are using.

None: extract from the project's CSS. The `:root` custom properties, the font-family
declarations, the colour palette, the spacing scale.

Either way the variants use these values verbatim. An invented hex code or font name is a
defect.

For the design judgement itself, read the `styleseed` skill when it is installed. Absent, the
axes table in `docs/SCREENS.md` is the standard. See `INSTALL.md`.

## Generate

`rules/mockups.md` assigns the slots and says who authors each. Launch the Codex slot in the
background before the Opus call, so it costs no waiting. Claude writes every file to disk,
including Codex's.

Codex echoes its prompt and prints its answer twice, so take the last delimited block and
trim at the final `</html>`. Read what came back before writing it: plain HTML, CSS and
minimal inline JavaScript, no external fetches. Anything else, or a missing `<html`, gets
regenerated by Opus, and the round continues.

## Judge

One judge agent, reading `docs/SCREENS.md` fresh at run time rather than from anything
quoted here. It scores each variant on its own, as that variant lands, and deduplicates
layouts that turned out functionally identical.

Survivors are counted against the bar in `rules/mockups.md`. Below it: respawn the rejects
naming the exact pattern matched, and ask for a different layout paradigm rather than a
different colour.

Codex grades the screenshot as a second judge. It advises; the first judge decides. Codex's
verdict on the slot it authored carries no weight.

Both judges picking the same variant is a high-confidence recommendation. A split is signal:
show both reasons, and build one crossover variant that keeps one parent's paradigm whole
and grafts named elements from the other. Averaging two layouts is banned.

## Show it

Screenshot the combined page and show it inline. Open it in the browser too.

## The gate

Ask **"Which variant? (or redirect)"** and wait. No production code before the owner names
one.

## Component sourcing

Before any build dispatch, emit one row per interactive element in the chosen variant: what
it is, and where it comes from. Elements come from the project's existing component library.
A hand-built row for something the library already provides is a gate failure.

Never install a second component library beside an existing one, and never block the build
on a library.

## Done

This stage has finished when the variant set in `rules/mockups.md` exists on one page, the
survival bar there is met, the screenshot has been shown, the owner has named one variant,
and the sourcing table is on screen.
